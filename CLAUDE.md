## 1. Project goal (the full prompt)

**Pubster** is a native iOS app (plus web dashboards and a backend) for discovering pubs and
their events, reserving tables, joining events, and pre-ordering food.

Original brief, captured verbatim in intent:

> Make an iOS app called Pubster in native Swift. It shows users the nearest pubs around them
> and the events happening at those pubs. People can reserve tables and be part of an event.
> There must be a menu, and people can pre-order food. Reservations use time slots. Wherever an
> event is going on, being part of that event can carry charges.
>
> Onboarding is phone number + OTP. For now the OTP is a **dummy** system: any phone number can
> log in with a dummy OTP — **but the user must be really registered in the DB** (for testing).
>
> There is also a pub/manager side with **two** logins:
> 1. A **general dashboard** (web, usable on computers/iPads) showing general reservation status,
>    orders, etc. Staff can add/remove tables here.
> 2. A **manager** login showing all the metrics and managerial tools. The manager sets the pub's
>    total table capacity (any number) and defines the table inventory — e.g. "2× 2-seat tables,
>    5× 6-seat tables," etc.
>
> Backend lives on our VPS and every backend service runs as a **PM2** instance. The project is a
> **monorepo** — iOS, backend, and everything else live in their own subfolders.

## 5. The four surfaces

1. **Consumer iOS app** — end users find pubs, browse menus/events, reserve tables, join events,
   pre-order food.
2. **General Dashboard** (web) — pub floor staff: live reservation status, order/pre-order queue,
   add/remove/edit tables, check-in guests.
3. **Manager Dashboard** (web, elevated role) — metrics + configuration: total capacity, table
   inventory, menu CRUD, event creation + pricing, staff accounts.
4. **Backend API** (VPS, PM2) — serves all three clients + the database.

## 6. Auth & roles

- **Consumer login:** phone number + OTP.
  - **Dummy mode:** any phone number is accepted; the fixed dummy OTP `000000` logs the user in.
  - **But persistence is real:** a genuine user row is created/looked up in the DB on every login,
    so downstream features behave realistically. Only SMS delivery / code verification is stubbed.
  - First-time consumers provide a **name** (phone is already known).
- **Pub-side login:** **email + password** (standard for web dashboards).
- **Roles / account creation:**
  - **Super-admin** (project owner) onboards a pub and creates its first **manager** account.
  - A **manager** invites/creates **general-staff** accounts for their pub.
  - Roles: `super_admin`, `manager`, `staff`, `consumer`.

## 7. Domain model (core concepts)

- **Pub** — name, location (lat/lng via PostGIS), address, hours, photos. Has its own menu, tables,
  and events.
- **Table inventory** — the manager sets a **total capacity** and defines tables by size, e.g.
  `2× 2-seat`, `5× 6-seat`. Tables are pooled by size, not individually assigned to guests.
- **Reservation** — grabs **a table of the right size from the pool** (not a specific table) for a
  **fixed 90-minute time slot**. A plain table reservation (no event) is **free** (no deposit) for MVP.
- **Event** — belongs to a pub; has a name, time window, **capacity cap**, and a **per-person cover
  charge**. A user "joins" an event **as part of a reservation** made during the event window,
  paying the cover charge for their party. (Model can be extended to standalone tickets later.)
- **Menu** — per pub; categories → items with name, price, description. **No modifiers/options** for
  MVP (item + price only).
- **Pre-order** — food ordered against a reservation's slot, **paid upfront** (stubbed). Staff work
  the order queue (preparing → ready → served).
- **Payment** — stubbed for MVP: an order/charge is recorded as paid without real money movement.

### Reservation availability logic (the flow)
1. User selects a **time frame** (date + slot) at a pub.
2. User enters a **party count**.
3. System finds the smallest table size ≥ party count and checks whether one of that size is
   **available** in that slot (inventory of that size minus reservations already holding it).
4. If available → user can book (and optionally join an overlapping event + pre-order food).

## 8. Userflows

**Consumer (iOS)**
1. Onboarding → phone number → OTP (`000000`, real DB user) → first-time name → location permission.
2. Discover → map + list of nearest pubs sorted by distance; "event tonight" badges.
3. Pub detail → photos/hours/address · Menu · Events · Reserve.
4. Reserve → pick time frame → enter party count → see availability → pick slot →
   *if an event overlaps: show per-person charge + option to join* → optional pre-order →
   review → pay (stubbed) → confirmation.
5. My bookings → upcoming/past, QR confirmation, modify/cancel.

**General Dashboard (staff)** → login → today's reservation timeline + live occupancy →
order/pre-order queue → tables (add/remove/edit) + live table status → guest check-in.

**Manager Dashboard** → login (elevated) → metrics (revenue, occupancy %, reservations, no-shows,
event revenue, top items) → capacity & table inventory config → menu CRUD → events (create,
capacity, cover charge) → staff account management.

## 9. Backend & deployment conventions

- Every backend service is a **PM2 process**, defined in `ecosystem.config.js`.
- Deploy = **commit → push → pull on server → deploy with `.env` → `pm2 reload`** (see §2).
- `.env` is never committed. Keep an `.env.example` in the repo documenting required vars.
- Prisma migrations run on the server as part of deploy (`prisma migrate deploy`).
- Currency is a config constant. **Assumption (confirm): `USD`.** Easily changed in one place;
  payments are stubbed so this is low-stakes for now.
- VPS assumed to have Node, PM2, PostgreSQL, and nginx (reverse proxy + TLS). **Verify on first
  connect; provision anything missing.** Repo may or may not be cloned there yet — verify first.
